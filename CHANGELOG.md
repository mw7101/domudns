# Changelog

All notable changes to DomU DNS will be documented in this file.

## [v0.5.1]

### Fixed

- **CLI banner:** `cmd/cli/main.go` still announced itself as `dns-stack-cli - Management CLI for domudns` — the pre-rename project name and a binary that does not exist (`make build` produces `domudns-cli`). Now `domudns-cli - Management CLI for DomU DNS`, in the `--version` output and the usage line as well. No test asserted the old strings.

### Changed

- **GitHub mirror: rebuild tooling.** Sanitizer and leak check moved into `scripts/github-sanitize.sh` (sourced library); `scripts/github-publish.sh` keeps only the git/push mechanics for a single release. The new `scripts/github-republish-tags.sh` plus the manual CI job `publish:github-rewrite` (main only) export *every* `v*` tag, sanitize and verify each tree, then rebuild the mirror's refs from scratch (`main` = newest tag, tags as sanitized snapshot commits). It builds and checks all commits *before* the first push, so a failed check aborts without touching the mirror. Needed because releases published before the leak-check repair still carry internal data. Verified as a dry run against a local bare repo: all ten tags rebuilt, each with 0 hits for every internal pattern, no committed binaries left, and the normal release path still lands on top of the existing mirror `main`. `docs/gitlab-ci-cd.md` documents what a tag triggers and when a rebuild is needed.
- **CHANGELOG (v0.5.0 section):** the section had grown seven category blocks with duplicated headings (`### Security`, `### Fixed` and `### Changed` twice each) — against the repo rule of one heading per category, and confusing in a release that is also the first thing visitors of the GitHub mirror read. Consolidated into `Added → Changed → Fixed → Security` (Keep a Changelog order). Content verified as unchanged: 65 content lines and 56 bullets before and after, only reordered.

### Security

- **GitHub publication (binary and extensionless files bypassed the check):** the check was a positive list of file types, and the list was incomplete a second time: `v0.3.0` and `v0.4.0` shipped a committed `domudns` build artifact at the repo root, whose Go metadata contains the internal module path. No list entry and no sanitizer rule ever saw it, and a binary cannot be rewritten in place anyway. Root build artifacts (`domudns`, `domudns-cli`, `dns-stack-cli`, `coredns`; `build/` and `dns-stack` were already deleted) are removed before publishing, and the check now runs by **exclusion** — only image/font formats and `.git` are skipped, everything else must be free of internal patterns. A new file type, a binary or an extensionless file can therefore no longer slip through unnoticed.
- **GitHub publication (sanitizer + leak check, follow-up to the check repair):** three families of internal data were still reaching the mirror because no rule and no pattern knew them. (1) The pre-rename module path `github.com/mw7101/domudns` and the bare project name `domudns` — the latter sat in `cmd/cli/main.go`'s user-visible banner *and* in four tracked editor leftovers (`cmd/domudns/main.go.bak`, `.bak2`, `.old`, `.orig`), which were published untouched because `*.bak*`/`*.orig`/`*.old` were in no file-type list at all; those leftovers are now deleted before publishing and their extensions are scanned by the check. (2) Internal host labels `s3-ext`, `pve-node`, `fw01`, `docker-host`, `s3-ui` (now `s3-ext`, `pve-node`, `fw01`, `docker-host`, `s3-ui`; word-boundary anchored so `docker0` or similar cannot be hit accidentally). (3) Home paths `/home/user`, `/Users/user` (quoted error output in the changelog, now `/home/user`, `/Users/user`). Also, `go.mod` is part of the sanitizing pass now instead of relying on the separate sed, and the check pattern `github\.com/maik/` covers both module paths at once. Verified by replaying the script's steps 1–5 in an `alpine:3.21` container against a copy of the tree: clean tree still passes, planted leaks and missing GNU grep both abort.

## [v0.5.0]

### Added

- **Cluster (self-healing URL domains):** The master state response now carries per-URL blocklist domain checksums (`url_domains_meta`: `{url_id, sha256}`), and a new HMAC-authenticated endpoint `GET /api/internal/url-domains/{id}` serves a URL's raw gzip domain set. On every poll a slave compares the master's checksums with its local `<id>.domains.gz` files and pulls only the stale or missing sets. This closes the last gap from the `url_domains` push timeout: a push lost for good previously left that URL's domains stale on the slave until the master's next fetch cycle (up to 24 h), because slaves never fetch external URLs themselves. The pulled bytes are written verbatim so the local checksum matches the master's, and the running blocklist is refreshed in memory.
- **Docs (website):** The REST API reference now documents DNS rate limiting (`system.rate_limit.dns_queries`, `exempt_networks`, `api_requests`), client access control (`dnsserver.allowed_networks`) and the `dns_queries_rate_limited_total` / `dns_queries_acl_denied_total` metrics, with live-reload `PATCH /api/config` examples (EN + DE).
- **DNS access control:** `dnsserver.allowed_networks` (CIDRs or bare IPs) restricts which client networks may query the DNS server. Empty (default) allows every client; when set, other clients receive `REFUSED`. Invalid entries are logged and skipped (never block startup); the list is live-reloadable via `PATCH /api/config` and refused queries are counted by the new `dns_queries_acl_denied_total` metric. Active ACME DNS-01 challenges (`_acme-challenge.*`) bypass the ACL so Let's Encrypt issuance/renewal keeps working — the certificate authority's validation resolvers are public and cannot be allowlisted; only stored, non-expired challenges are exempt. Dashboard settings tab exposes the allowlist.
- **DNS query rate limiting:** `system.rate_limit.dns_queries` (sustained queries per minute per client IP, initial burst equal to the limit) is now actually enforced. New `dnsserver.QueryRateLimiter` — a token bucket per client IP with a bounded map (50k entries, 10-min idle eviction, fail-open under map pressure to protect the 1 GB target hardware) — runs before the pipeline and answers `REFUSED` when a client exceeds its allowance. `system.rate_limit.exempt_networks` (CIDRs or bare IPs) bypasses the limiter, e.g. for a router that forwards the whole LAN's queries from its single IP. Wired through `dnsserver.Config` and the live `PATCH /api/config` reloader; refused queries are counted by the new `dns_queries_rate_limited_total` Prometheus metric. Set `dns_queries: 0` to disable. Previously the setting was parsed and exposed via the API but never enforced. Dashboard settings tab exposes all three fields.
- PowerDNS-compatible REST API (`/api/pdns/v1/servers/{server_id}/zones[/{zone_id}]`, `GET`/`PATCH`) for third-party ACME DNS-01 tooling (Proxmox VE "DNS-01 PowerDNS API" plugin, acme.sh `dns_pdns`) that can only speak the PowerDNS Authoritative HTTP API; independent of and unchanged from the existing `/api/acme/dns-01/*` endpoints. Auth also accepts the `X-API-Key` header (PowerDNS convention) on every endpoint now, not just this new one. See `docs/powerdns-compat.md`.
- Let's Encrypt TLS via ACME DNS-01: automatic certificate provisioning and renewal for the HTTP/API server. Master acquires certificate, syncs it to slaves via cluster push (EventTLSCert) and poll fallback. Zero-downtime hot-reload via `tls.Config.GetCertificate` + `atomic.Value`. API: GET/PUT `/api/tls/acme`, GET `/api/tls/acme/status`, POST `/api/tls/acme/renew` (async, 202 Accepted). Exponential backoff on failure (1h→24h). Certificate and ACME account key stored in `{data_dir}/tls/` with correct file permissions (0644/0600).
- Client-Gruppen-Policies: per-client-group blocklist categories (ads, malware, adult, social, gambling, tracking). IP ranges can be assigned to groups with different categories enabled. Default behavior (no match): ads + malware active. API: GET/PUT /api/client-groups. Blocklist URLs now accept an optional category field. Cluster-synced via EventClientGroups.
- Zone cloning: `POST /api/zones/{domain}/clone` clones an existing zone with all records to a new domain and/or view. SOA is freshly generated; all other zone metadata is copied. Dashboard: clone button in zone list and zone detail, with modal for new domain/view input.
- Zone detail view: search field above the records table to filter records by name, type, or value; SOA row is hidden when results are found, visible when no records match
- Dashboard: new "TLS / Let's Encrypt" settings tab for configuring ACME DNS-01 certificate provisioning. Shows domain, email, staging toggle, certificate status (expiry date with remaining days color-coded green/yellow/red), last renewal timestamp, renewal error box, and manual renewal button. Slave nodes see a read-only view with info banner.

### Fixed

- **Docs/Website (Go-Version):** after the Go toolchain moved to 1.27.3, the documented build requirement still said "Go 1.24+" in `README.md`, `docs/deployment.md` (both the prerequisites and the build machine section) and the website quick start (`website/docs/quickstart.html`, the prerequisite list *and* the `schema.org` HowTo JSON-LD). Anyone following those instructions would have built against the standard library that still carries the 34 CVEs fixed in 1.27.2/1.27.3 — the exact gap the toolchain bump closed. All four places now state `Go 1.27.3+` (and mention that `go.mod` requires that patch level). The historical planning notes under `docs/superpowers/plans/` were left untouched on purpose: they record the stack as it was when those plans were written.
- **DNS (ALIAS):** the ALIAS phase resolved its target with a direct `ForwardTracked` call, so the upstream answer that gets synthesized into the client's response bypassed rebinding protection (Phase 5.5), DNSSEC preparation/`ProcessResponse`, and singleflight deduplication — the last documented gap of the same class as the CNAME chase fix. A public ALIAS target resolving to a private IP was served (measured: plain query → NXDOMAIN, same name via ALIAS → NOERROR + `10.0.0.5`). `resolveAliasUpstream` now goes through the shared upstream path (`forwardRequestDeduped`) and applies the rebinding check against the canonical target plus DNSSEC processing; a blocked answer is answered with NXDOMAIN instead of the synthesized records, on both ALIAS entry points (`aliasPhase` and a CNAME chain ending in an ALIAS, `pipeline_cname.go`). Regression tests: `TestAliasPhase_UpstreamTarget_RebindingBlocked`, `TestAliasPhase_ChainEndingInAlias_RebindingBlocked`, `TestAliasPhase_UpstreamTarget_PreparesDNSSEC` (asserts the DO bit on the upstream request); the fake upstream test helper was split so a test can observe what is sent upstream.
- **DNS (ALIAS without a record of the queried type):** an ALIAS whose target resolved but held no record of the queried type answered **SERVFAIL** where NODATA was correct. Because stub resolvers query A *and* AAAA in parallel, an A-only target broke the whole lookup on musl: on docker-host `ping s3-ext.example.local` and `busybox nslookup` failed with `bad address`/`SERVFAIL` while `getent` (which tolerates one failing address family) resolved fine — so pointing `example.local` records at the `cln` zone via ALIAS fixed nothing for Linux clients. `aliasPhase` now answers NOERROR with an empty answer when the target simply has no record of the queried type (RFC 2308 §2.2), and keeps SERVFAIL for a lookup that actually failed. A target owned by a local zone is no longer sent upstream either: its authoritative answer is final, so an internal name is not leaked to a public resolver. Regression tests: `TestAliasPhase_TargetWithoutQueriedType_IsNODATA`, `TestAliasPhase_LocalTargetWithoutQueriedType_NoUpstreamQuery`, `TestAliasPhase_UnresolvableTarget_IsServfail`.
- **DNS (CNAME chase hardening):** three follow-ups to the out-of-zone CNAME chase below, found in review. (1) A chased upstream answer bypassed phase 5.5 and DNSSEC: `cnamePhase` called the forwarder directly, so a public canonical name resolving to a private IP was blocked on a plain query but **served** through a CNAME (measured: `evil.example.net` → NXDOMAIN, `gw.rebind… → CNAME → evil.example.net` → NOERROR + `10.0.0.5`), and the AD bit/DNSSEC RR filtering never ran. The phase now uses the shared upstream path (`forwardRequestDeduped`, extracted from `forwardUpstreamDeduped`: DNSSEC `PrepareRequest` + singleflight dedup) and applies `ProcessResponse` plus the rebinding check to the canonical name before appending the answer. (2) A chain ending in an **ALIAS** record dead-ended as CNAME-only — the same `EAI_NONAME` failure the chase exists to prevent. The ALIAS's A/AAAA records are now synthesized under the ALIAS's name (the ALIAS itself stays invisible, R8), sharing `resolveAliasRRs`/`synthesizeAliasRRs` with the ALIAS phase. (3) The in-zone part of the chain only counted depth, so a loop (`a → b → a`) emitted 18 CNAME RRs — duplicate RRs, against RFC 1035 §3.6.2, and needlessly large UDP answers (before the chase: 1). Every name followed is now tracked in a `seen` set seeded with the queried name, so the chain is cut at the first repetition and the answer carries two distinct CNAME RRs.
- **DNS (CNAME with an out-of-zone target):** a CNAME whose canonical name lies outside the queried zone was answered with the CNAME record only, so clients that do not follow CNAMEs themselves failed with `EAI_NONAME` (`ping: bad address`): musl/Alpine (`ping`, `busybox nslookup`) and glibc `getaddrinfo` (Debian 13 container, Node's `dns.lookup`), while macOS/mDNSResponder and public recursors masked the problem by re-querying the canonical name. The same-zone chase added earlier (`zones.go`'s `appendCNAMEChainAnswer()`) looked up targets in `zone.Records` only, so it stopped at the zone boundary — which broke every `example.local` record pointing into the `cln` zone (`s3-ext`, `pve-node`, `fw01`, `s3-ui`) for Linux clients. The chase now follows chains across zones: the new `cnamePhase` (`internal/dnsserver/pipeline_cname.go`, pipeline phase 3.4) resolves the canonical name `GenerateResponse()` reports (`zoneResponse.cnameTarget`) in the other local authoritative zones — view-aware and following further CNAMEs across zones — and, for A/AAAA, via the upstream forwarder. The CNAME RR(s) stay in the answer and the appended records keep their canonical owner names. Chains are bounded by `maxCNAMEChainDepth = 8`; a loop or an unresolvable target returns the CNAME chain unchanged (NOERROR), i.e. exactly what a plain authoritative server answers, so no client that copes with CNAMEs regresses.
- **CI/CD (Website-Deploy):** `deploy:website` brach ohne gesetzte `WEBSITE_HOST`-Variable sofort ab (`ssh-keyscan -H ""` → `usage: …`, exit 1) — die eigentliche Ursache blieb im Log unsichtbar. Der Job prüft die Pflicht-Variablen jetzt vorab und meldet fehlende Werte im Klartext. Deployt wird außerdem **per Compose** (`docker compose pull && docker compose up -d` auf `${WEBSITE_COMPOSE_FILE}`, Default `/srv/docker/domudns/compose.yml`) statt per `docker run`: Die Website läuft auf dem Webserver als Compose-Service (`domudns-website-1`, Port 84→80) hinter nginx-proxy-manager; ein `docker run -p 80:80` wäre am dort belegten Port 80 gescheitert und hätte einen zweiten, nicht Compose-verwalteten Container angelegt. Die Default-Werte (`WEBSITE_USER=maik`, `WEBSITE_SSH_PORT=22022`, Compose-Pfad, `WEBSITE_URL`) setzt jetzt die Shell statt GitLab: GitLab kennt die Shell-Syntax `${VAR:-default}` in `variables:` nicht und expandierte sie zu `""` — in Kombination mit `docker compose -f ''` ergab das den irreführenden Folgefehler `read /home/user: is a directory`. Neu sind zusätzlich der SSH-Port (der Server lauscht nicht auf 22, `ssh-keyscan` bekam den Port vorher gar nicht mit) und ein abschließender HTTP-Health-Check gegen `WEBSITE_URL`.
- **Record names / ACME DNS-01 (PowerDNS-compat API):** `dns.ValidateRecord` accepted only a single-label record name, so a zone-relative name like `_acme-challenge.pve-node` (the ACME DNS-01 record for `_acme-challenge.pve-node.<zone>`, written by Proxmox VE's "DNS-01 PowerDNS API" plugin / acme.sh `dns_pdns`) was rejected with `ErrInvalidLabel` and the compat `PATCH` returned `422` — silently swallowed by acme.sh, which does not use `curl --fail`, so the challenge timed out with the hook still reporting success. Names are now validated by the new `dns.IsValidRelativeRecordName` (`@`, or one or more dot-separated labels), so ACME DNS-01 also works for hosts below the zone apex, and `zone_importer.go` no longer silently drops deeper names during import. Multi-label record names containing `*` (e.g. `*.dev`) are now rejected: a `*` label only acts as a DNS wildcard when it is a record's sole label, so such a name would be stored but never match. Out-of-zone records (e.g. `www.other.net` inside zone `example.com`) are again skipped on zone import instead of being stored un-servable. The compat `PATCH` also **clamps** a requested `ttl` below the new `dns.MinRecordTTL` (300 s) to 300 instead of returning `422` — acme.sh's default `PDNS_Ttl` is 60. See `docs/powerdns-compat.md`.
- **PowerDNS-compat API (canonical path):** The PowerDNS-compatible API is now also served at the canonical `/api/v1/servers/{server_id}/zones...` path, so acme.sh's `dns_pdns` hook and the Proxmox VE "DNS-01 PowerDNS API" plugin can reach it. Previously it existed only at `/api/pdns/v1/...`, which no acme.sh-based client ever requests — the hook always builds `/api/v1/servers/<ServerId>/zones?zone=<name>` and aborted with `invalid domain` on the resulting 404. The legacy `/api/pdns/v1/...` path is retained as an alias and behaves identically. Added a no-op `PUT .../zones/{zone_id}/notify` endpoint (`204`) so the hook's post-write `notify_slaves()` step succeeds instead of failing zone-id validation with `422`. Corrected `docs/powerdns-compat.md`: the Proxmox plugin's `API URL` field must be the **host only** (acme.sh appends `/api/v1/servers/<ServerId>/...` itself).
- **Cluster (push):** Raised the default `cluster.push_timeout` from 5 s to 30 s and added a bounded retry (delays 0/2 s/5 s, up to 3 attempts) for transient push failures — transport errors and 5xx are retried, 4xx is terminal. A large blocklist URL (100k+ domains) is cleaned and gzipped on the slave *before* it answers `/api/internal/sync`, which can exceed 5 s on a Raspberry Pi 3B; the too-short timeout produced spurious `context deadline exceeded` warnings and risked a lost `url_domains` update (URL domains are not part of the poll state, so they have no fallback). Successful retries are logged at info, individual failed attempts at debug.
- **Cluster (slave):** Same-kind reload callbacks are now serialized and coalesced. `triggerReloadCallback` started a fresh goroutine per change, so if the master state changed again while a reload (e.g. zone or blocklist) was still running, two reloads of the same kind could run concurrently. The poll loop now uses a per-kind `reloadScheduler`: at most one run per kind at a time, and a trigger arriving mid-run schedules exactly one follow-up run (the follow-up reads the store after the write, so the newest state is still loaded). Different kinds remain independent. The slave **push receiver** (`ReceiverHandler`) now shares the same scheduler via `ReloadCallbacks.WithSharedReloadScheduler()`, so poll-driven and push-driven reloads of the same kind no longer overlap either; the receiver's 30 s reload timeout is preserved (a timeout returns an error, so a hung reload cannot wedge the scheduler).
- **Website / README (DNSSEC):** Removed false "DNSSEC signing" claims. DomU DNS only performs AD-flag delegation (RFC 4035): it sets the DO bit upstream and propagates the upstream's AD bit — it does not sign zones or validate locally. Corrected the feature card, FAQ, comparison table, JSON-LD structured data, and README.
- **Cluster (test):** `TestApplyMasterState_AppliesSectionsAndTriggersCallbacksOnce` and `TestApplyMasterState_IgnoresAbsentAndNullSections` used plain `int` counters incremented inside reload-callback goroutines and read from the test goroutine, producing `WARNING: DATA RACE` under `go test -race`. Counters are now `sync/atomic.Int32` (test-only change, no production code affected).
- **Cluster (slave):** Poll loop no longer triggers `BlocklistReloader`, `ZoneReloader`, and `DDNSKeyReloader` on every 30-second tick when the master state has not changed. SHA256 checksums of each state section are tracked between polls; callbacks only fire when bytes actually differ.
- **Cluster (slave):** `EventURLDomains` no longer triggers a full disk reload of all blocklist gzip files. The slave now applies URL domain updates in-memory (`BlocklistManager.ApplyURLDomains`), eliminating the `cluster: blocklist reload timed out` error that occurred on Raspberry Pi 3B after each blocklist fetch cycle.
- HTTP server now correctly starts on HTTPS :443 when a TLS certificate is available (ACME or static), and on HTTP :80 when no certificate is loaded yet. Previously the server always used whatever port was configured in `caddy.listen` (default :80) even in HTTPS mode, causing TLS handshake errors on port 80 and an unreachable port 443 that broke health checks and cluster slave polling.
- Slave node now fails to start with a clear fatal error when `DOMUDNS_SYNC_SECRET` is not set, preventing silent sync rejection at runtime
- `GET /api/health` on a slave node returns `{"status":"degraded"}` when the HMAC sync secret is not configured, so the dashboard correctly reflects cluster misconfiguration
- **DNSSEC:** `PrepareRequest` no longer creates a second OPT record when the client request already carries one. `SetEdns0()` always appends a new OPT instead of replacing an existing one; the DO bit and UDP size are now set on the client's existing OPT in-place. Previously, upstream resolvers that enforce RFC 6891 (e.g. Unbound) returned FORMERR for any client query that already included an OPT record and had DNSSEC forwarding enabled.
- **CAA records:** `recordToRR()` validated the CAA flags range (0-255) after truncating to `uint8`, so the check could never trigger and an out-of-range value silently wrapped around instead of falling back to 0. The range check now runs on the original `int` value before truncation.
- **Zone export (CAA):** `zone_exporter.go`'s `buildExportCAARR()` cast `Priority` to `uint8` without the same range check `recordToRR()` already had, so a corrupted/out-of-range CAA flag value could export as a different byte than it would serve live. - **Dashboard:** `deleteNamedAPIKey()` in `lib/api.ts` never checked the response status, so a failed named-API-key deletion (403/404/500) still showed a "deleted" success toast in the Security tab. It now checks `res.ok`/401 and throws `ApiError` like every other mutation in the module.
- **Zone writes (TOCTOU/lost update):** `PUT /api/zones/{domain}`, the record PUT handler, and the PowerDNS-compat `PATCH` handler each loaded a zone via `GetZone`/`GetZoneView` (a short-lived read lock), ran validation/merge logic with no lock held, and then saved via `PutZone`/`PutRecord` (a separate, new write lock) — a concurrent write to the same zone (another API request, DDNS update, or cluster receiver) could commit in the unprotected window and be silently overwritten. Added `store.ZoneWriter.UpdateZone(ctx, domain, view, mutate)`, which holds a single write lock across load, mutate, and save; `PropagatingStore.UpdateZone` propagates `EventZoneUpdated` only after a successful mutate. All three handlers migrated; HTTP status codes and error semantics are unchanged.

- **Cluster replay protection** (`internal/cluster/`): `SyncRequest` now carries a Unix-nanosecond timestamp and a 16-byte random nonce. Both fields are bound into the HMAC. ## [v0.1.1]

### 2026-03-07

#### Added
- **RFC 2136 DDNS fully operational** — ISC dhcpd integration end-to-end working. DNS records are created/updated automatically from DHCP leases via TSIG-authenticated RFC 2136 UPDATE messages.
- **DDNS runtime statistics + dashboard** (`internal/dnsserver/update.go`, `internal/caddy/api/ddns.go`, `dashboard/`): `DDNSStats` struct tracks total updates, failures, last error and rejection reason. `GET /api/ddns/status` exposes these stats. Dashboard shows a 4-card stats grid with contextual diagnosis banners (NOTZONE, NOTAUTH) and a dhcpd config guide (pre-filled `dhcpd.conf` snippet with key name and algorithm).

#### Fixed
- **DDNS UPDATE packets rejected with NOTIMP** (`internal/dnsserver/server.go`): miekg/dns `DefaultMsgAcceptFunc` rejects `OpcodeUpdate` (5) before the handler is called. Fixed by setting a custom `ddnsMsgAcceptFunc` on all server instances (UDP, TCP, DoT).
- **TSIG key lookup failing silently** (`internal/dnsserver/update.go`): `UpdateKeys()` and `GetSecrets()` now add trailing dots to key names in `TsigSecret`. miekg looks up keys as FQDNs — without the trailing dot the lookup silently failed, causing every UPDATE to be rejected with NOTAUTH.
- **TSIG signature missing from responses** (`internal/dnsserver/update.go`): `respond()` now calls `resp.SetTsig()` before `WriteMsg()`. miekg only signs responses when the response message already contains a TSIG RR — without this, dhcpd reported `expected a TSIG or SIG(0)` and treated successful updates as failures.
- **Duplicate records on dhcpd retries** (`internal/dnsserver/update.go`): `applyUpdate` for ClassINET now uses upsert semantics — existing records with the same name+type are deleted before inserting the new one. Previously, dhcpd retries created duplicate A/TXT records.

#### Tests
- `TestDDNS_TsigSecret_TrailingDot`: trailing-dot regression test for `UpdateKeys()` / `GetSecrets()`.
- `TestDDNS_Stats_SuccessfulUpdate`, `TestDDNS_Stats_NotZoneRejection`, `TestDDNS_Stats_NotAuthRejection`, `TestDDNS_Stats_AccumulatesAcrossMultipleCalls`: DDNS stats unit tests.
